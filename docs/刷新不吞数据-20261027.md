## 根因与修复

发布环节没有版本管理的补充输入，也没有旧 id 防丢门禁，源数据以外的记录无法从重建恢复。当前默认分支小时脚本本身从旧 goods.json 回灌价格；真正从 categories 重建的入口也存在于日采集。两条路径都必须保护，不能只改注释或只手工恢复产物。

- `data/supplements/goods-supplements.json` 是受 git 管理的数组，显式从 `.gitignore` 排除。含 168 款 `model_reference`（`price=null`、`discontinued=true`）及完整 28 条分类商品。每行都有 `source`、`catalog_identity`。
- `goodsdex.supplements` 在写文件前校验、合并。补充 id 在重建结果中存在时只记冲突，完整保留重建行。补充文件丢失、补充 id 重复、任何旧 id 消失均失败。
- 强制校验 `count == rebuilt_count + added_count`；重新计算 `count / brands / with_price / by_kind`。小米品牌缺省按 `CN:mi_cn:` id 识别，不沿用以前已失真的 brands 数字。
- 小时刷价和 `goodsdex.publish.build` 共用该逻辑。停售模型不参加取价及回灌，避免 null 价格被变成在售价格。顺便修复 market_price 缺省时调用 `int(None)` 的崩溃。
- 两个 workflow 保留默认分支已有的品牌采集步骤和共享发布互斥组。开始保存上版 goods.json，所有品牌发布步骤结束后再做最终防丢检查，并再次计算四项统计。
- 去掉自动 `rebase -X theirs` 和可能假成功的推送重试。普通 push 遇到远端并发变化直接失败，需要基于最新 data 重跑校验，不强推、不择边覆盖。
- 如果日采集缺少任何其他品牌旧 id，也会阻止发布并列出缺失 id；不会为了发布成功放松防丢规则。
