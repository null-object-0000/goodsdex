# 任务：评估 REA 对**现有采集链路**有没有优化价值（不是找 SKU）

> 上一轮我做错了一件事：把 REA 这条线用去做了 SKU 反查，那是另一个问题。本任务要回答的是委托方真正的问题——**REA 能不能让我们现在的小米/Apple 采集做得更好、或更快定位漏采**。

## 0. 现状（先读代码，不要重探）

本仓 `src/goodsdex/` 已实现的入口：小米商城 PC/移动商品详情、搜索接口、批量价格接口；Apple 采集适配器；详情长图参数靠视觉提取。上一轮调研见 `docs/SKU反查与停产机型调研.md`（含 3.62 分钟定位判定基线、33 次请求账本、频率纪律）。

**已知的、可验证的采集缺口**（本任务就用这两个当靶子，别自己另找）：

- **缺口 A（小米）**：商品详情的"图文长图"里的参数，现有链路靠视觉提取，成本高、易漏。问题是：长图背后的数据到底有没有结构化来源（接口/脚本里的字段），还是真的只在图里。
- **缺口 B（Apple）**：规格页里尚未解析的部分（如 AirPods 5、iMac 定制配置的更细规格）。问题是：这些字段在页面/脚本/接口的哪一层，现有采集为什么没覆盖。

## 1. 要做的事（严格按顺序）

### 步骤 1：先打基线（不装 REA）
用你现在就有的工具（直接 HTTP + 已配置的 chrome-devtools MCP）分别处理缺口 A 与缺口 B，各自记录：
- 从开始到**拿到结论**（能定位到结构化来源 / 或确认只在图里）的墙钟分钟数；
- 关键请求或脚本位置，能否写出可复现的样例；
- 卡在哪一步（如果有）。

### 步骤 2：装 REA 并做同一目标
`npx rea-agents setup --client codex`（可用 `--skill=false`；若交互确认无法非交互通过，就按 REA 官方文档手动注册 MCP，**必须先备份 `~/.codex/config.toml`**）。装完记录：
- 安装版本、注册方式、改动了哪些配置文件、**卸载/回滚的确切命令**；
- 是否需要 Ghidra/Hopper（我们只做 Web/JS 分析，应不需要——若 setup 要求装 Hopper，**中止并如实报告**，不要装重型依赖）。

然后用 REA 处理**同样的两个缺口**，同样记墙钟分钟数与结论。

### 步骤 3：对照
给一张对照：同一缺口，两种方式的耗时、结论是否一致、REA 额外看到/漏看了什么。**只比这次实测到的**，不要拿 README 的能力清单当结果。

## 2. 要回答的问题

1. REA 能不能**发现现有采集漏掉的字段或入口**？两个缺口各自给"能/不能/部分"，并给证据。
2. 定位耗时缩短了多少？（用步骤 1/2 的分钟数）
3. 它的结论**需不需要真实请求复核**才可用？（它自己的文档说需要，用这次实测印证或推翻）
4. 代价：配置侵入、是否需要重型依赖、能否干净卸载、对日常采集有没有副作用。
5. **结论**：值不值得作为"采集排障/发现入口"的工具长期接入；如果值得，**在什么场景用**、什么场景不该用（例如每小时刷价这种已知路径）。

## 3. 纪律

- 只碰公开页面与公开接口，不带账号/cookie；同一端点请求间隔 ≥2.1 秒；总请求控制在几十次内。
- 不修改采集器代码、不改定时任务、不动 `data` 分支、不 push。
- 不许把"REA 宣称的能力"写成"实测结论"；没测到的写"未验证"。
- 装 REA 是可回滚的：报告里必须写清卸载步骤，并且确认它没有常驻进程/服务。
- 交付 `docs/REA采集增益评估.md`，一笔提交（含该文档；`docs/TASK-sku-lookup.md` 之类已存在的未跟踪任务书一并提交或忽略，别动别的文件）。
