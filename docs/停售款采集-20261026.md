# 小米 / 米家「停售 / 历史款」采集取证

日期：2026-10-26，北京时间。网络账本覆盖约 12:47–13:01；文档与离线校验在其后完成。

**结论：值得建立独立历史采集线；已跑通“官方旧 sitemap → 旧导航身份与规格链接 → 移动接口明确下架 → 官方规格页”的 60 款闭环，但它不能覆盖 2018 年之后的全量历史款，厨房秤的官方参数也仍未恢复。**

这里的 `discontinued` 仅表示**本次官方商城明确下架**，不代表停产、其他渠道停售或产品失效。没有用搜索缺席、年代、无库存、`is_enable=false` 单独判定停售。

## 1. 四个问题的答案

### 1.1 能不能枚举停售清单？

**没有验证到“直接枚举全部停售款”的官方清单；验证到可以枚举的历史候选清单，并能逐款确认下架。**

#### PC API 为什么有人拿到非 JSON：Referer 的四格对照

以下请求不跟随重定向、不带登录 Cookie。请求 URL 都是 `https://api2.order.mi.com/product/view?product_id=18426`，所有完整请求头均在账本。

| UA | Referer | 请求编号 / HTTP | 响应 |
|---|---|---|---|
| 桌面浏览器 | `https://www.mi.com/` | R0005 / 200 | JSON，code=-50011 |
| `curl/8.0` | 空 | R0239 / 406 | `请求来源不合法`，非 JSON |
| `curl/8.0` | `https://www.mi.com/` | R0326 / 200 | JSON，code=-50011 |
| 桌面浏览器 | 空 | R0327 / 406 | `请求来源不合法`，非 JSON |
| 移动浏览器 | `https://m.mi.com/` | R0240 / 200 | JSON，code=-50011 |

**本环境中可复现的原因是 Referer 校验，不能归因为 UA 或“这个 pid 被一律封锁”。** 这组样本没有 302，也没有 HTML 跳转；用户其他环境的非 JSON 如果不等于这个 406 文本，仍需对照其真实状态/Location，不能把所有非 JSON 都归为同一原因。

正向控制：[pid 19963 的 PC 详情](https://api2.order.mi.com/product/view?product_id=19963&version=2)，R0241 HTTP 200、业务 code=200。这进一步说明 PC 接口整体可读，18426 的资料缺失是另一个层次的问题。

### 1.3 停售款参数还在不在？

**部分仍在官方旧规格页，移动详情删掉不意味着静态规格页一定消失。**

| 数据 | 本次能得到什么 | 不能推断什么 |
|---|---|---|
| 名字 | 60 款来自官方旧导航；厨房秤名称来自用户输入，来源独立注明 | 空响应不能靠 pid 编名字 |
| 型号 | 18 款取得单一、可归属的官方型号。例如 pid 3674，规格页 R0270 HTTP 200，`<b>产品型号：</b><span>BPM1</span>`；pid 7522，R0297 HTTP 200，型号 `AC-M5-SC` | MIOT model、铭牌型号、商城 pid 不能互换；同页多个型号不擅自选第一项 |
| 参数 | 29 款共 379 对官方 HTML 文本标签/值；例如 R0266 的 `<b>CPU</b><span>四核 Cortex-A35 1.3GHz</span>` | 不读营销图猜规格；未命中模板不等于官方没有参数 |
| 价格 | 21 款保留 `last_known_price`：来自官方旧导航的非零展示价，并核对关联规格页仍 HTTP 200、标题/品名相符；币种按小米国内商城元计，保留字符串原值 | 无法确认这个展示价的生效日期、是否最后成交价、是否曾促销；0/空值不当价格 |
| 历史价格序列 | 全部 `price_history=null` | 旧导航单个价格不是价格历史 |
| 最后在售日期 | 全部 `last_seen_on_sale=null` | `fetched_at`、sitemap lastmod、社区发布时间都不是最后在售月份 |

所有停售记录的 `price` **一律 null**。`last_known_price_context` 明示“官方旧导航当前仍返回的展示价；非最后成交价，日期未知”，并附价格来源和仍可访问的页面证据。

参数解析仅支持两类已验证文字结构：单一规格表、`p > b + span`。电视页发现 `MITV_SPECS_TYPE` 和多个 `mitv-specs-*` 面板时先选尺寸；无法确定面板或同标签出现不同值时整页暂不入参数。电动牙刷页同时列主体 `DDYS01SKS` 与刷头 `DDYST01SKS`，因此本轮参数留空，避免把配件型号归给主机。多型号字符串也不塞进单一 `model` 字段。

**厨房秤最终字段：** `product_id=18426`；用户提供的 name；`discontinued=true`（R0008）；`model=null,params=[],price=null,last_known_price=null,price_history=null,last_seen_on_sale=null`。没有采用任务示例中的 `2026-04`。

### 1.4 规模与成本

**建议按“千级历史候选”规划，粗估约 1,000–3,000 个候选型号键；这不是已证实的独立停售机型总数。** 依据是：2018 sitemap 已有 1,443 个商城商品 ID；社区仅“米家”“小米”关键词就分别有 893 / 464 个设备模型结果（两者可能重叠），全生态产品 sitemap 有 10,353 项。小米/米家非联网产品、手机与较新产品并不由社区完整覆盖，而社区也混有其他品牌与接入变体。故不能把 10,353 当小米历史款数，也不能证明准确去重后必然超过一千；几千条候选是工程预算估计，置信度中低。

本轮限定 sitemap 中 pid < 10,000,000 的 680 个候选，按原顺序处理前 126 个，成功率 60/126=47.6%。另外 763 个高位 ID 暂未纳入本轮批采，**不能统称为套装**：R0247 HTTP 200 明示 `10000085` 的名字为“小米MIX 2S”。它们需要另做 family/单款映射与去重。该前缀样本并非随机抽样，不能用 47.6% 精确外推全库。

- 对一个已有正确 pid 的候选：旧导航身份 1 次 + 移动状态 1 次；若可归档，再抓已链接规格页约 1 次，合计通常 3 次。重定向、模板脚本或重试另计。
- 按本轮候选损耗，不共享调研缓存：1 次 sitemap + 126 次身份 + 61 次状态 + 60 次规格页 = 248 次逻辑请求，约 **4.13 次/成功样本**；厨房秤试点另 1 次。首次找入口的研究成本单独计算。
- 1,000 款成功样本按本轮命中率约 4,100 次请求；常规批次仍须每轮 ≤600，分批运行。下架状态复核通常 1 次/已知 pid，不必每次重抓静态规格。
- 2.12 秒同主机间隔、串行执行下，1,000 款的初采应预留数小时；仅同主机间隔与约四千请求的量级已不适合一次短任务。网络延迟、失败退避与人工补模板另计，不能按“找到 API 就近乎免费”估算。

## 4. 复跑、纪律与校验

标准库实现，无新增运行时依赖。已保存证据的零网络完整重建：

```bash
python3 scripts/crawl_archive_history.py --crawl --target 60 --enrich --pilot --validate --offline
python3 scripts/crawl_archive_history.py --research --offline
python3 tests/test_archive_history_crawl.py
```

不加 `--offline` 时优先复用证据缓存，仅补缺失请求。`--refresh` 强制重新取证，仍受同一账本的累计预算限制；不会偷偷清空计数。首次采集可用同一完整命令去掉 `--offline`。这只是有界证明脚本，跨日期批次的证据轮换、增量调度与全量去重尚未做成生产调度。
