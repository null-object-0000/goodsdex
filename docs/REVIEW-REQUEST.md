# GoodsDex 项目评审请求

## 背景

GoodsDex 是一个**商品数据索引**项目：给定一个商品分类（如"吹风机"），枚举出全部商品，从多个数据源采集数据，合并成**每条数据都能追溯来源**的结构化数据集。

最终目标（下游用途）是做一个「这东西该不该换/该不该买」的判断工具——不仅能比参数，还要算使用成本、算换代盈亏平衡点。所以数据的**准确性、可溯源性、可比性**是硬要求。

## 目前已实现的

### 1. 数据源（都可工作）

| 源 | 内容 | 获取方式 |
|---|---|---|
| 小米官方-移动端 | 参数最全（含发布日期、销量、口碑标签、买家秀、问答） | `POST m.mi.com/mtop/xiaomishop/product/info`，需 4 个自定义头 + `[{},{...}]` 数组体 + gid |
| 小米官方-PC | 图文详情、购买选项 | `GET api2.order.mi.com/product/view?product_id=X&version=2` |
| 百度百科 | 精确到日的发布时间、代际定位 | 无头浏览器（curl 被 403） |
| ZOL | 第三方参数 | HTML 标签配对 + 噪声清洗 |

**已排除**：小米国际站/香港站——区域版本，型号体系与国行不同（港版型号 `M2535E1` 未必等于国行），配色命名也不一致，混入会污染型号主键。

### 2. 核心原则

- **三路并查**：抓任何页面前先看 raw HTML / 渲染后 DOM / 网络请求。小米 PC 商品页的 raw 是空壳，真数据在 `product/view` 接口里——只有看网络请求才发现。
- **字段级溯源**（不是记录级）：每个字段独立记录 站点/页面/UI位置/接口/JSON路径/抓取时间。
- **严格匹配**：第三方源按名称查找时，词条名必须与商品名完全一致。模糊匹配（0.77 相似度）曾把「REDMI Buds 8 青春版」匹配到「REDMI Buds 8 Pro」。
- **冲突留痕**：不静默覆盖，分类为「表述差异」（同一事实不同说法，如 `约5.3g` vs `5.3±0.1g`）和「数据矛盾」（真正对不上）。

### 3. 关键代码结构

```
src/goodsdex/
  model.py       Record / Provenance / Conflict / 源优先级
  normalize.py   字段归一化（别名合并、嵌套参数展开、冲突判定）
  probe.py       CDP 三路并查探测器
  pipeline.py    主流程（分类 -> 枚举 -> 多源 -> 归一化 -> 输出）
  sources/
    mi_cn.py     小米官方（PC + 移动端）
    baike.py     百度百科
  parse/
    html.py      HTML 标签配对 + JS 注入噪声清洗
```

## 当前遇到的问题（希望重点评审）

### 问题一：商品字段是「固定 + 动态」混合，当前模型没有区分

实际数据：

```
吹风机（4款）：每款 33 字段，全是通用元数据 + 参数混在一起
耳机（4款）：26 / 46 / 46 / 46 字段
  - REDMI Buds 8S 只有 26 字段 —— 官方 classParameters 返回空数组（参数 0 项）
  - 其他三款 46 字段 = 26 通用 + 20 品类参数
```

拆开看：

- **通用元数据**（~26 项，固定）：`name` / `price` / `market_price` / `颜色` / `img_url` / `carousel` / `qa_items` / `review_tags` / `commodity_id` / `sku` …
- **品类参数**（动态）：吹风机是 `最大风速` / `马达转速` / `最大噪音` / `护发因子`…；耳机是 `降噪` / `续航_单次` / `防水` / `蓝牙协议` / `发声单元`… **两套毫无交集**

参数名**完全由官方数据源的 `classParameters` 决定**，产品不预设。

**所以「一个商品有 35 个字段」是含糊甚至错误的说法。** 我倾向把 Record 拆成：

```python
Record:
  meta:   通用元数据（固定 schema）
  params: 品类参数（动态 dict）
  schema: 该品类的参数维度定义（可选，用于对比时对齐）
```

但不确定这是否最优。另外还有个发现：小米官方有个 `classes.tab_classes` 接口，返回**每个品类的参数维度定义 + 每个维度的全部可选值**（如手机品类给 CPU型号/CPU主频/后置摄像头…）。这应该被利用起来，而不是把字段写死在代码里。

### 问题二：空参数 vs 采集失败没有区分

`REDMI Buds 8S` 参数为空是**数据事实**（官方还没录），不是 bug。但当前实现两者长得一样。

### 问题三：跨品类/跨机型对比的对齐规则未定义

想比「吹风机 A vs B」，需要取参数字段并集，缺失显示"未提供"。但更麻烦的是**语义对齐**——比如耳机的 `降噪=55dB` 和吹风机的 `最大噪音=73dB` 是两个不同概念，不能因为名字里都有"噪"就放一起。
