# GoodsDex 整体评审请求（第 2 轮）

## 这是什么项目

商品数据索引：从小米商城官方采集商品数据，建成**字段级可溯源、冲突留痕、可验证**的结构化数据集。最终服务于「这件东西该不该换/该不该买」的判断。

**当前阶段：采集与对比链路已打通的原型**。86 个分类、2191 款商品、19 次提交、9 套测试 89 项。
（第 1 轮评审见 `docs/REVIEW-codex.md`，当时指出的问题已修，本次请审**当前状态**。）

## 运行方式

```bash
export PYTHONPATH=src:scripts     # 未打包
python3 -m goodsdex.pipeline --category 吹风机      # 采集单分类
python3 scripts/crawl_all.py --resume              # 全量采集
python3 scripts/compare_all.py 耳机                 # 跨商品对比
python3 scripts/audit_usability.py                 # 数据可用率审计
python3 scripts/vision_params.py --category 挂壁空调 --limit 3 --write
for t in tests/test_*.py; do python3 $t; done      # 9 套 89 项
```

数据在 `data/categories/*.json`，每分类一个文件，含 `captures` / `assertions` / `view` 三层。
依赖：Pillow；百度 OCR 凭据在 `~/.config/herelens/keys.env`；视觉网关 `127.0.0.1:18640`（本机，可能不可达）。

## 核心设计

```
Capture     一次采集的完整证据（原响应 + 状态 + 内容哈希 + 时间）
Assertion   谁对哪个属性、在什么条件下声明了什么（locator 定位到原响应）
View        按策略选出的展示值（可重建，不是事实本身）
```

适配器返回**断言列表**，不按字段名去重 —— 同值多源是独立佐证。
状态区分 `success / partial / transport_error / rate_limited / source_error / parse_error`；
缺口原因区分 `source_empty`（源未提供）/ `absent`（确实没有）/ `not_collected`（采集失败）。

## 请重点审查的 6 处

### 1. 分类解析 `sources/mi_cn.py::list_categories`

正则解析分类页 HTML。**曾漏掉 10 个大类**（手机/电视/笔记本/平板/穿戴/耳机/家电/路由器/音箱/配件）——
原因：只认 `<span class="text">` 形式，而导航区是纯文本 `<a>耳机</a>`。现两种都解析（84 → 94 类）。

**这个解析可靠吗？还有别的链接形式没覆盖吗？用正则解析 HTML 的结构性风险？**

### 2. 分页枚举 `sources/mi_cn.py::enumerate_products`

曾把响应里的 `total`（全局匹配数 57）误当成「可发现数量」，而实际在售结果在 `pc_list`（空）。
现用 `stop_reason` + `completeness` 区分，新增 `no_sellable_items` 语义。
PC 源有 429 限流熔断（进程内，连续 5 次开路）。

**分页逻辑还有隐患吗？熔断设计合理吗？**

### 3. 选图策略 `scripts/vision_params.py::find_spec_images` —— 我最没底的地方

**曾经犯的严重错误**：用「排除服务类 tab」的排除法，结果全库 23197 张候选图里
**16516 张（71%）来自 `tab='商品详情'` 的营销图**，导致把「全面升级」「10年免费包修」
当成产品参数提取。这是本项目最严重的一次数据污染风险。

现改为白名单分层：
- tier1：tab 名含"参数/规格"（实测 1641 张）
- tier2：tab 名是具体型号（"256L(星锻银)"、"直冷-186L"，实测 4815 张）
- 其余不取。候选降到 6456 张。

**问题：这个白名单会不会太窄漏掉真规格图？tier2 的判据（`GENERIC_TAB` 排除法）可靠吗？
有没有比"按 tab 名猜"更可靠的办法？**

### 4. 视觉提取与归一化 `vision_extract.py` / `vision_normalize.py`

长图按 1700px 切片送本机视觉网关；结果标 `mi_cn_pc_vision`，**不覆盖**接口值。
归一化处理同一事实的多种写法（`额定制冷量(W)` / `（W）` / ` (W)`），
并分离包装清单（7号干电池/使用安装说明书）。

**别名表是手工维护的。随品类增多会不会失控？有更好的做法吗？**

### 5. 已做的实测结论（请审查推理是否站得住）

- **混合模式无增益**：把 OCR 文本连同图片一起给视觉模型，
  项数没增加（39 < 44）、耗时涨 1.5-3 倍（161s vs 68s）、
  结果与纯视觉逐项相同。推测：图片已含全部信息，OCR 是冗余同源描述。
- **几何特征不足以判断排版**：能效标识图几何上像表格（行内多块 0.82、字号统一），
  但语义上标签与值错位，OCR 结果崩坏（`"1级"→"11级"`、`"王"→"能效标识中国能效标识"`）。
  改用「配对污染率」（值里含键的文字）作主判据。
- OCR 在规整两列表格上 0.6s 可用（vs 视觉 21s）；在标识/图文混排上不可用。

**这三个结论的推理成立吗？有没有幸存者偏差（样本量小）？**

### 6. 换机经济模型 `economics.py`

一手依据：小米官方《保值换新服务条款》（保值率 50%/部分 60%、服务窗口第 181-395 天、
回收方是转转）。输出净掏钱、日均成本、盈亏平衡天数、窗口状态；缺残值时拒绝判断。

**模型有无经济学上的错误？「盈亏平衡天数」这个概念站得住吗？**
