# 商品库分片（2026-10-29）

实现工作树：`/tmp/goodsdex-shards-20261029`（数据管道）、`/tmp/spend-good-shards-20261029`（服务端）。原工作区未提交改动未改动。

## 结构与契约

数据分支路径为 `public/`，OSS 对应 `data/public/`。`goods.json` 保留为整库导出，客户端继续使用 search / goods/<id>；整库 API 保留 `x-payload-warning: full-catalog`。

`index/<品牌>.json` 是 `{items, query_gzip}`：items 白名单保留身份、分类、价格、图、品牌及服务端匹配实际需要的轻字段，**没有 params**。query_gzip 为 gzip + base64 的查询投影数组，与 items 一一对应，包含原始行顺序、精确搜索文本、规格分面及列表展示所需的少量值。原搜索会查询参数内的任意字串，因此必须保留查询文本；压缩整个品牌投影可复用同族重复文本，服务端只还原文本和轻投影，不解析完整参数对象。启动不会读 detail 或 goods.json。

`detail/00.json` 至 `detail/3f.json`：按 `uint32(sha256(id)[0:8]) % 64` 定位，key 为原 id，value 为完整原始首条记录。实质冲突同 id 的其余记录放在首条记录的 `_catalog_conflicts` 中，接口读取时移除此内部字段；因此 95 组冲突的全部原始行均未丢失，详情仍沿用旧服务端选择第一条、合并分类的规则。goods.json 保持全部 3,762 行，唯一 ID 3,608 个。

`meta.json` 包含 schema=1、generated_at、count、unique_count、detail_sharding、files（每文件 sha256/count/bytes），保留原有品牌统计和审计。meta 是提交标志，其自身不做自引用哈希；同步端另算 meta SHA-256 作为本地代际 ID。

品牌映射在 `src/goodsdex/shards.py:BRANDS`。没有 brand 的旧记录按要求进入 other，包括旧小米记录；不为凑品牌文件而改原始字段。mi_cn 文件当前为空，服务端品牌分面仍按原规则识别小米。未知品牌也进入 other。

## 发布和同步

四条现有发布任务均在最后的 finalize_public.py 中完成去重守卫后生成分片，goods.json 不重写。OSS 上传前校验所有散列，先写永久保留的 `blobs/<sha256>.json` 并 GET 回读验证，再写具名文件，最后写 meta。不能删除旧 blobs：旧索引的惰性详情仍需取对应版本。

服务端先取 meta，按 SHA-256 复用本地未变化索引，只下载变化索引。所有索引完整校验（含查询投影解压）后，原子替换 catalog-current.json 指针；坏分片、未知 schema 均保留旧代际。price/history 维持原有独立同步机制。

详情、ids、gids、product_ids 按需读取 hash 分片，校验后落盘；最近 200 条详情采用 LRU，并按索引代际隔离。完整导出也按需下载，冷启动不取 14MB。首次同步只取索引，不预载任何详情。按内容哈希获取详情，避免小时发布后旧索引混入新详情。

商品同步流量（不含独立价格快照/历史）：旧版每轮 14,065,303 字节 goods + meta；新版首次索引 3,157,776 字节 + meta 9,299 字节，减少约 77.5%。无变化只传 meta；单品牌变化只传 meta + 对应品牌文件。首次详情额外读取命中分片，后续本地命中无网络。镜像阶段上传的是发布产物，不能与服务端同步流量混为一谈。

## 性能口径

每个版本各启动一个全新 Node 进程，导入相同模块后创建索引，load 后执行第一次 group_products 查询。没有清操作系统页缓存，因此这是**进程冷启动**，不是磁盘断电冷启动；本地文件读盘测试不包含 OSS 网络时间，不能冒充完整容器启动收益。

| 索引 load | 303.94 | 288.66 |

## 新增品牌与回滚

新增品牌：采集器发布原始记录；在 shards.py 的 BRANDS 中加显示名到安全文件名的映射（不加也会进入 other）；如有新的列表事实来源，同步更新 FACT_KEYS/查询投影并通过全项验收。服务端遍历 manifest，无需为每个品牌改加载代码。若改变定位算法、投影字段语义或详情值结构，提升 schema 并同步更新服务端解码器。

回滚点：数据源保留 goods.json，服务端旧读取实现 e77a8a4；远程部署脚本会备份旧代码和旧镜像。恢复旧镜像即可按旧读取路径工作；如需最新完整导出，先从 OSS goods.json 恢复本地 /data/goods.json。新代码的 schema=1 选择由 catalog-current.json 决定，手动测试旧路径时移走该指针并使用旧 meta/goods 成对快照。不要仅删索引文件。原始整库与详情 blobs 不删，回滚不涉及商品数据迁移。

旧容器真实冷启动一次：2026-10-29T03:34:00Z，启动到外部 health.json 可用 3,534ms，其后首次 group_products HTTP 查询 93.76ms（服务端原有自预热保留）。本地单次 CPU 初始化没有稳定的大幅改善，主要确定收益是每轮网络传输从 14MB 降至约 3MB；不把拆分解释成所有查询耗时均按体积比例下降。
