# 任务：攻「SKU → 商品」的官方接口，以及停产机型入口

## 0. 为什么是这两件事（比 Apple 规格页值钱）

产品侧实证：用户铭牌上的 SKU（`BHR4945CN`、`BHR7504CN`、`E4501CN`）与型号（`AC-M17-SC`、`P27QCA-RG`）在 GoodsDex 公开集里**精确查 0 命中**；而停产机型（如 Redmi G27Q 2025）在售集里根本不存在。这两件事卡住的是「拍铭牌 → 认识这台东西」，也是录入自动化的唯一现实入口。

## 1. 要回答的问题

### Q1：小米商城有没有「按 SKU 反查商品」的可用路径
- 目标 SKU（真实、来自用户铭牌）：`BHR4945CN`（米家空气净化器 4 Lite）、`BHR7504CN`（追觅全能基座）、`E4501CN` 或 `ELA5501CN`（Redmi 显示器 G27Q 2025，两个写法都试）。
- 试探对象：小米商城（`mi.com` / `m.mi.com`）站内搜索、商品详情页参数区、`api.mi.com` 之类公开接口、以及页面脚本里出现的接口候选。
- 判定：能拿到什么（商品名 / productId / 型号 / 价格 / 是否在售），需不需要登录态，是否被 robots 或风控拦。**给出可直接复现的请求样例与真实响应（截断到关键字段即可）。**

### Q2：停产/历史机型能不能拿到
- 目标：`Redmi 显示器 G27Q 2025`（铭牌型号 `P27QCA-RG`）。
- 试探：米家/小米商城的搜索接口能否按型号串命中已下架商品；有无历史/全部商品列表入口（分页、筛选、`main_sort` 之类参数）；厂商官网的"产品库/旧款"页。
- 判定：给结论「能/不能/只能到某一步」，并说清断在哪。

## 2. 方法与纪律

- **只用公开页面与公开接口**；不带任何用户账号、cookie、登录态；不绕验证码、不做高频请求（同一接口间隔 ≥2s，总请求数控制在几十次内）。
- 优先用你已经配置好的 chrome-devtools MCP 观察页面与请求；也可直接 curl。**每一步都记时间**：从开始到定位到（或判定没有）目标接口用了多少分钟。
- 现有采集器（`src/goodsdex/`）已经掌握的入口不要重复探，先读代码再动手。
- 不许把未验证的接口写成"可用"；请求失败的把状态码与错误信息原样贴出来。
