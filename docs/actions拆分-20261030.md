## 合并与并发

选择「采集各自产出候选文件，publish 统一合并」。采集 job 只有 contents:read，读取 data 快照，不执行 finalize、不推送。候选以同一次采集的基线和变更组成，只包括 goods、价格历史、归档和采集缓存。meta/index/detail/merge-audit 等生成产物禁止进入候选。

共享发布 job 在 `goodsdex-data-publication` 并发组内持锁执行，`cancel-in-progress: false`，`queue: max`。锁覆盖：读取最新 data → 合并字段差量 → 门禁 → 唯一 finalize → 一次提交全部分片 → 推 data → OSS 校验回读。不能把同一组锁同时放在 caller 上，否则 caller 等待 callee 会自锁。

`queue: max` 是必要补充：GitHub 默认只保留一个 pending，单独设置 cancel-in-progress:false 仍会替换等待者。官方说明：<https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency>。最多排队 100 个，满队列会明确取消；这是平台限制。

按 ID 分组，对唯一行按字段做三方合并，保留其他品牌及采集期间新发布的无关字段；已知冲突 ID 的多版本作为一组保留。同一字段被两次独立采集改为不同值则失败，要求重跑该品牌，禁止旧候选回滚新价格。JSONL 只允许追加，按观察小时去重。完整差量先校验、后写入临时检出目录。跨品牌修改和任何未批准的 ID 丢失直接失败。

所有既有 data 写入者（包括 crawl-all / legacy / cars）都改用此入口。只读镜像恢复也持同一把锁，避免旧镜像覆盖刚发布的新版本。共享发布重新生成 supplement audit，先检查 no-lost-ID，再执行 verify_goods_release，最后 finalize（墓碑、字段归一、去重、分片）和 OSS 全文件摘要校验。汽车入口检查非汽车对象不变，其他入口继续检查汽车数量、类型和完整对象不变。

每个候选 artifact 按 run_id 命名，采集重跑覆盖该 run 的旧候选；只重跑失败发布 job 时仍能下载原候选（不依赖 run_attempt）。门禁、推送或镜像失败均会使 job 明确失败。镜像失败可单独重跑发布；不能自动 force push。

## 惠普耗时处理

拆分前最近一次 run 41126483126 的 HP step 实际 18 分 2 秒，整个 workflow 22 分 56 秒。因此不能沿用全量图片下载并只抬超时。小时刷新新增 `--reuse-images`：复用上一轮成功图片检查，继续实时 GET 每条配置与价格，新图片仍走原验证。每日全量不启用此参数，仍重新校验图片。未放宽商品、墓碑或分片门禁。
