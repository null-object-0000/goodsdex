# GoodsDex 设计评审

评审日期：2026-10-08。范围：`docs/REVIEW-REQUEST.md`、`README.md`、`docs/methodology.md`、`src/goodsdex/` 全部 Python 代码、现有测试，以及本地 `data/吹风机.json`。判断基于当前工作区，未请求外部网站，未验证接口今天是否仍可用。未修改采集代码或已有数据。

## 1. 目标是否合理，模型方向对不对

**目标合理，但当前实现是小米商城的采集原型，还不是可靠的多源商品索引。** 字段级溯源、保留冲突、优先防止错配，方向正确；“给一个分类，枚举全部商品”目前没有成立的范围和完整性定义。下游买换决策要求的不只是参数多，而是每个数值属于哪个商品版本、何时成立、在什么条件下测得，以及证据能否重放。

### `meta + params` 值得做，但不够

把通用信息和品类参数分开，有助于展示、统计和校验。但请求中那“26 项通用元数据”不应整体成为同一层：

| 数据 | 实际归属 | 原因 |
|---|---|---|
| 品牌、产品名称、品类 | 产品实体 | 描述产品身份 |
| 型号、地区、电压、容量、颜色、SKU | 型号/变体 | 决定比较的对象是否相同 |
| 现价、划线价、库存 | 商家报价及其时间快照 | 不是商品永久属性 |
| 转速、续航、防护等级 | 带条件的参数断言 | 同一参数可能有不同模式、测试方法和来源 |
| 评论数、标签、问答 | 站点反馈快照 | 可能按产品族聚合，不能直接当成单 SKU 的客观表现 |
| 图片、轮播、说明书 | 证据或展示资源 | 数量不代表参数覆盖率 |

建议让 `Record` 成为查询/导出的视图，底层保留事实断言。早期无需微服务或图数据库，用本地不可变快照 + JSONL/SQLite 就足够。逻辑上至少区分：

```text
Product / Variant        内部身份，地区、版本、销售变体和外部 ID 映射
Capture                  请求上下文、响应快照、采集状态及时间
Assertion                谁对哪个实体、哪个属性、在什么条件下声明了什么
AttributeDefinition      属性语义、类型、单位、适用范围和版本
ResolvedRecord           按策略选出的展示值，引用全部候选断言
```

一个参数断言可以是：

```json
{
  "id": "a1",
  "subject_id": "variant:example:cn",
  "attribute_id": "earphone.battery.single_playback_duration",
  "raw_label": "降噪关短续航",
  "raw_value": "8小时",
  "normalized_value": {"type": "quantity", "value": 8, "unit": "h"},
  "qualifiers": {"anc": "off", "volume": "unknown"},
  "evidence": {
    "capture_id": "c1",
    "locator": "$.data.goodsInfo.goodsList[0].classParameters.list[3].value"
  },
  "normalization_rule_version": "earphone-v1"
}
```

`meta` 和 `params` 可从这些断言生成；报价、反馈、资源独立输出。品类 schema 应通过 `schema_id + version` 引用，不必每个商品复制一份。固定 schema 也允许字段缺失，不应强行填满。

### 官方字段负责发现，项目负责语义

“参数名完全由官方决定，产品不预设”适合采集层，不适合比较层。**原始层开放，标准层有约束。** 没认出的字段照样存，但不能凭名字相似自动进入可计算参数。

请求提到的 `classes.tab_classes` 值得接入，作为属性发现、候选枚举值和 UI 选项的来源；本仓库尚无对应实现。不能默认其返回值就是完整规格 schema：需要验证它是否只是搜索筛选维度、是否覆盖下架产品和新值、有没有稳定属性 ID、单位和适用条件。保留源 schema 的快照和版本，再映射到内部属性定义。新值不在旧枚举中时，应标记并保留，而不是删除。

## 2. 当前实现的问题

### 2.1 严重：多源值还没进入冲突检测就可能丢失

位置：`pipeline.py:33`、`:38`，`model.py:66`，`normalize.py:126`。

- 两次 `raw.update()` 用字段名当唯一键。两个适配器返回相同字段名时，后一个直接覆盖前一个值和证据。
- `Record.set()` 也是覆盖语义，没有“同一字段多个断言”的容器。
- `flatten()` 在子字段和顶层同名时，只保留顶层。参数内部同名字段在 `fetch_mobile()` 的 dict 推导式里也会被覆盖，分组和条目位置一起丢失。
- 即使两个源给出完全相同的值，归一化也只保留第一个来源，第二个支持证据丢失。

**“保留 conflicts”补救不了合并前已经丢掉的事实。** 适配器应返回断言列表，不能返回用属性名去重的字典；选值必须发生在保存全部候选之后。

### 2.2 严重：官方双源价格实际不会对账

位置：`normalize.py:55`、`:163`；`model.py:115`。

`ALIAS` 写了 `pc_price -> 价格`，但 `STRUCTURAL` 中的 `pc_` 前缀先命中，直接保留原字段。离线输入移动端价格 `100`、PC 价格 `200`，结果是 `价格=100` 和 `pc_price=200`，没有价格冲突。`pc_name` 等也会绕过别名映射。

`FIELD_PRIORITY`、`DEFAULT_PRIORITY`、`SOURCE_LEVELS` 没有参与归一化选值。实际策略是字典遍历时的第一项，不是文档声明的字段优先级。

修复前先核对两端的具体 SKU、币种、促销条件和采集时间；不同变体或不同时间的报价属于不同上下文，不一定是矛盾。

### 2.3 严重：一旦检出冲突，输出可能失败

位置：`pipeline.py:49`，`model.py:75`；`normalize.py:165`。

`normalize_record()` 返回 `list[dict]`，却直接赋给声明为 `list[Conflict]` 的 `rec.conflicts`。`Record.to_dict()` 对每项调用 `to_dict()`，产生冲突时抛出 `AttributeError: 'dict' object has no attribute 'to_dict'`。离线用 `型号=A`、`model=B` 已复现。

采集异常写入 `_mobile_err` / `_pc_err`，却没有 `Provenance`，归一化会留下 `None` 来源，序列化同样可能失败。诊断应进入采集结果，不应伪装成商品字段。统一模型边界，至少验证“冲突记录”和“失败记录”可以序列化、读回并再次导出。

### 2.4 严重：归一化在主动制造语义错误

位置：`normalize.py:12`、`:84`、`:112`。

已通过离线输入验证：

| 输入/规则 | 当前结果 | 问题 |
|---|---|---|
| `降噪开短续航`、`降噪关短续航` | 都归为 `续航_单次` | 合并了不同工作模式 |
| `蓝牙编解码` | `蓝牙协议` | codec 与连接协议不是同一维度 |
| `上市日期`、`发布时间` | `发布日期` | 开售与发布是不同事件 |
| `最大风速测试条件` | `最大风速` | 子串匹配把测试条件当数值属性 |
| `5g` 与 `5kg` | 表述差异 | 忽略单位，实际相差千倍 |
| `5h` 与 `5h/30h` | 表述差异 | 第一数字相同掩盖额外语义 |
| `无主动降噪` 与 `主动降噪` | 表述差异 | 包含关系掩盖否定 |

`护发因子` 把负离子、水离子等归在一起，也不适合直接计算比较。`货号` 不应普遍等同制造商型号。

取消全局子串自动归并。映射按 `source + category + raw_attribute` 定义；数量先解析单位、范围、误差和条件，文本否定必须保留。比较结果至少增加“条件不同/无法判定”，不要强迫所有差异落进“表述差异/数据矛盾”二选一。`约5.3g` 与 `5.3±0.1g` 可以展示为可能兼容，但前者并没有明确误差界限，不能据第一数字相同就证明事实相等。

### 2.5 严重：溯源是说明文字，还不是可重放证据

位置：`mi_cn.py:128`、`:171`，`normalize.py:126`，`baike.py:75`。

移动端把 `list[{name,value}]` 转成 dict，再由 `flatten()` 拼出 `list[].最大风速`。原响应数组里没有这个属性路径，无法按该路径直接取回原值。`flatten()` 构造新 `Provenance` 时还遗漏了旧 `fetched_at`，读历史数据时会变成当前时间。

冲突 variants 只存 `source/raw_field/value`，没保留各自的页面、定位和采集时间。正常采集不保存原响应，也没有 capture ID、内容哈希、解析版本和标准化版本；`probe_out` 的探测产物没有与记录建立证据引用。

应该在解析数组时就为每个条目记录真实索引或稳定条目 ID，保留原始标签和值，引用完整响应快照。定位是相对于原始快照的，不是相对于解析后的临时 dict 的。转换不能修改采集时间。只保存 URL 无法证明网页过去说过什么。

### 2.6 严重：缺失、错误、空结果和不支持混在一起

位置：`mi_cn.py:114`、`:178`，`pipeline.py:31`。

非成功业务码返回 `{}`，PC 请求异常也返回 `{}`；调用方仍添加 `sources_used`。离线验证两端都返回空字典，记录依然声称使用了两个源。带 gid 的第二次移动端请求失败时退回第一次结果，没有标记降级。

建议区分两个层次：

- 采集任务状态：`success / partial / transport_error / source_error / parse_error / not_found / unsupported`，携带响应码和错误详情。
- 数据可用性：`provided / source_empty / absent / explicitly_unknown / not_applicable`。来源未成功读取时，展示“采集失败”，不能展示“未提供”。

HTTP 和业务响应成功、结构经过校验且 `classParameters.list=[]`，只能证明**该响应当时参数列表为空**，不能证明“官方还没录入”的原因。字段缺失和类型变化需要另外报告结构漂移。

`is_junk()` 把“无”“暂未公布”和空集合全部剔除，也损失语义。“降噪=无”可能是明确的不支持；空参数列表是有效采集结果。保留原断言，展示层再决定怎么显示。

### 2.7 商品身份和枚举范围尚未建模

位置：`model.py:54`，`mi_cn.py:59`、`:71`、`:127`、`:188`。

`product_id` 是源内商品键，不是跨源产品主键。移动端取 `defaultGid` 后仍选择 `goodsList[0]`，PC 也选择第一项；没有验证它们指向同一销售变体。颜色选择器的全部颜色与当前 SKU 的颜色也混在同一记录中。本地样例的 `Record.name` 来自带颜色的搜索标题，而 `data.name` 是不带颜色的产品名，说明实体层次尚未明确。

分类目前转成关键词搜索，无法承诺分类全集：可能混入配件，遗漏别名、旧款、下架型号。枚举异常直接 break、达到页数上限也直接返回，没有记录完整性；缺失 `total` 时默认 0，可能第一页就结束。不能把短列表当成“这个分类只有这些商品”。

先明确索引宇宙，例如“中国大陆小米商城本次搜索可发现的商品”；输出发现来源、查询、页数、total 原值、停止原因及 `complete/partial/unknown`。产品身份应有内部 ID、外部 ID 命名空间、地区和变体映射；现阶段只存国行也应明确写 `market=CN`。

完全一致的名称只能用于候选筛选，不是实体同一性的证明；同名可能不同区域、年份或套装，搜索标题也可能带颜色。百科目前只校验搜索结果 URL 的 slug，没有验证抓取后的标题、跳转落点和型号；显式传入 URL 更会绕过匹配。保留匹配依据和审核状态，优先核对型号/制造商 ID，而不是放宽名称相似度。

### 2.8 文档夸大了实际的多源能力

`pipeline.py` 只导入、执行小米源，`--sources baike,zol` 不会调用百科或 ZOL，也不拒绝这些选项；当前文件树没有 `sources/zol.py`、`parse/text.py` 或 `tools/probe.py`。HTML 解析工具和 ZOL 探测文件不能等同完整适配器。

百科 `fetch()` 需要调用方先提供 HTML/text；仅找到 URL 不会自动抓页面。搜索依赖 `hermes_tools`，仓库没有依赖安装清单。README 的 `python3 -m goodsdex.pipeline` 对干净环境也缺安装或 `PYTHONPATH=src` 的前提。

先如实描述已接入能力，让未知/未接入源立即报错。源适配器统一输出采集结果和断言即可，不必先做复杂插件框架。

### 2.9 百科“精确日期”有比缺失更危险的错误

位置：`baike.py` 的 `parse()` 和 `fetch()`。

全文第一个带发布/上市动词的日期被当作发布日期，没有验证句子说的是哪个产品。离线输入“前代产品于2020年1月2日发布。本产品于2026年10月8日发布”，输出却是 `发布日期=2020-01-02`，来源描述还写“信息框发布时间”。这不是可靠溯源，而是给错误提取包装了一段来源说明。

评审过程中该文件有外部更新：已删除全文任意日期的兜底，复核后公司成立日期反例不再产生发布日期。因此不把该已修复行为列为当前缺陷；上述前代日期误取在更新后仍可复现。

按信息框结构或明确正文句子提取，保留原句、实体指代、事件类型及日期精度。发布、上市、开售分别建模。缺乏直接证据就不输出日期；第三方精确到日不应自动压过官方到月，更不能用任意日期补全月份。

### 2.10 探测器与运行可靠性

`probe.py:75` 的 `_send()` 在等待命令响应时丢弃其他 CDP 消息；`inspect()` 导航时、取响应体时都调用它，可能丢掉网络事件。取 body 的时机是 `responseReceived`，响应体可能还没下载完，应等 `loadingFinished`；XHR 判断使用 `r.get('body')`，但 body 实际存放在另一个 dict，会漏掉 URL/MIME 未命中特征的请求。也未处理 `base64Encoded`。

应有统一事件分发和命令响应路由，导航前开始接收事件，下载结束再取 body。当前探测器可以帮助发现接口，但不能把“没看到请求”作为“没有数据”的证明。探测是适配器开发工具，不必每个商品每次跑三路。

采集运行还缺失败清单、有限重试、按站点限速和运行 manifest；失败商品被跳过，输出仍像完整成功，整份 JSON 覆盖写入且并发顺序不稳定。先做到每个枚举实体都有结果或失败状态，稳定排序、临时文件原子替换并保留批次记录，再优化并发。

## 3. 面向索引、溯源、对比的补充建议

### 对齐单位之前先对齐语义和上下文

比较键应是“属性 ID + 实体层级 + 条件”，不是中文字段名，也不是单位。耳机 ANC 衰减与吹风机噪声即使都用 dB，也没有直接可比性；噪声还可能需要计权方式、距离、档位等条件。续航要区分 ANC、音量、编码、单耳/整套；IP 等级要指明耳机还是充电盒。

同品类比较取内部属性集合的并集，原始未知字段另列。单元格引用断言，显示具体缺失原因、证据和冲突状态。条件不同则并排展示而不是强行排优劣。跨品类仅在显式定义的共同维度或用户任务上比较，不自动把相似文字归成同一参数。

没有统一测试条件的官方最大值，只能做“厂商标称值对照”。需要性能排名时，引入测试方法一致的实测断言，与标称值分开。

### 让质量指标对应下游价值

“33 字段”“0 冲突”没有质量保证：图片和内部 ID 能撑高字段数，误并、漏接源又能降低冲突数。按品类定义少量决策关键属性，分别统计采集成功率、参数覆盖率、身份确认率、可定位证据率、可比条件覆盖率、过期率和未解决冲突。分母来自版本化的比较 schema，不是本次响应恰好出现的键。

本地吹风机样例还包含“用的什么芯片？”“日用还是夜用？”等问答文本；它们与吹风机语境不协调。这不足以断言接口错了，但应触发响应与产品身份复核，不能因为来自官方就自动信任。

### 冲突保留和展示选值分开

选值策略需要版本、理由和候选引用；可以偏向官方，但不能把官方优先当成永远正确。官方 PC/移动端可能共享上游，不是两个独立佐证。方法文档中的重量错标案例也说明：来源等级只能是一个因素，还需要属性语义、证据直接性、版本和时间。无法判断时允许没有唯一选值。

每次采集追加历史，分别记录采集时间和来源声明的有效时间。价格变动是时间序列，不是自动形成冲突；同一时点、同一变体、同一条件下的互斥断言才需要对账。人工确认要留下决策记录，不修改原始证据。

### 买换判断要额外建模输入和假设

参数索引不能单独回答“该不该换”。还需要旧设备状态、实际使用频率、寿命/维修概率、耗材、当地能源价格、购买费用、残值、性能需求，以及对体验改善的估值。

例如吹风机省电成本应估算 `功率(kW) × 每次使用时间(h) × 使用次数 × 电价`，额定功率并不等于实际平均功耗，高功率也可能缩短使用时间。未知输入应给区间或情景分析，不应补成 0。回本计算保存引用的参数断言 ID、报价快照、公式版本和用户假设；净节约不为正时明确没有有限回本期。

先选一个品类完成可核查的 A/B 比较闭环，再决定是否扩展到更多品牌和品类。不要以来源数代替闭环质量。

## 4. 如果只能做三件事

按下面顺序做。前三项应成为三个可验收的里程碑，不是一次重写全部系统。

### 第一：建立不丢证据的采集闭环

以现有小米双源为范围，增加 `Capture/FetchResult` 与断言列表，保存原响应和真实定位；错误、空数据、降级分别记录。修复冲突/失败序列化及 `pc_` 绕过，未知源直接拒绝。不要在此阶段新增网站。

**验收：** 同名不同值、同值多源、空参数、业务失败、网络失败五种离线样例都能导出并读回；每个候选能定位原始快照；采集时间不会被归一化刷新；失败不会伪报成功；历史不会被覆盖。

这是第一优先级，因为丢掉的证据以后无法靠更好的规则补回。

### 第二：明确商品身份和索引边界

定义产品/地区版本/销售变体关系，给现有外部 ID 加命名空间，核对移动端 gid、PC goods 和价格归属。为发现过程记录范围与分页完成状态，让所有枚举结果都有成功或失败记录。第三方接入前先过实体匹配门槛。

**验收：** 不同颜色、不同 SKU、不同地区和同名不同型号不会误合；每份列表说明“从哪里发现、覆盖到哪里、是否完整”；名称提示与标准名称分离；两端报价对比指向同一已确认变体。

这是第二优先级，因为证据再完整，挂到错误商品上仍然没有价值。

### 第三：做一个品类的类型化参数和 A/B 对比

先做吹风机，定义决策相关的少量属性 ID、类型、单位和条件，替换全局子串别名和第一数字冲突规则；输出含缺失原因、原始值、条件和证据引用的对比表。官方维度接口作为 schema 发现输入，有条件再接入，不让它阻塞闭环。

**验收：** `5g/5kg` 不会被判等，不同测试条件不会强比，未知值不会进入计算；明确不存在的能力不被当垃圾丢掉。保留跨品类反例，确保耳机降噪不会进入吹风机噪声维度。报告分别统计元数据、参数与可比关键属性覆盖率。

这是第三优先级，因为前两步保证“谁说了什么、说的是谁”，这一步才保证“这些值能否比较”。买换计算等对比层站稳后再做。
