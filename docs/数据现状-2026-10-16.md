| 项 | 实测 |
|---|---|
| 商品档案 | **3,915 条**（整机 1,973 / 配件 1,088 / 服务 114 / 未判定 740），价格覆盖 **99.4%**（3,892） |
| 生成时间 | 2026-10-16 07:46 |
| 采集分类 | 95 个，状态全部 `ok`，商品合计 3,500（`_progress.json`） |
| 下架留档 | ✅ 有（`data/archive/`，95 个文件，与 categories 一一对应） |
| **价格时间序列** | ⚠️ **只有 7 天**：2026-10-09 21:44 → 2026-10-16 15:16，**31 个快照** |
| 序列覆盖 | 1,831 个商品有价格记录；其中 **1,519 个有 ~26 个点**（密集），7 个有全部 31 个点 |
| 价格字段 | `price` / `market_price` / `min_price` / `max_price` |
| **残值（旧机估值）历史** | ❌ **没有**。转转是**现查现用**（`sources/zhuanzhuan.py`），不落库 |

### 判断
- **商品档案够用**：三千多条、分类全覆盖、有下架留档。
- **价格历史太浅**：7 天算不出「跌价速度」。换新决策的核心是**未来 180 天的折损**，
  折损率需要长期价格曲线或二手行情曲线 —— **7 天不够**。
- **残值曲线缺失**：没有历史估值，回答不了"这台机器一年跌了多少"。

## 二、增量数据（管线）

| 项 | 实测 |
|---|---|
| 价格刷新 | 每天实际 **3-5 次**（README 写"每小时"，实际达不到 —— Actions 的 cron 会延迟/丢任务，workflow 注释里也记了） |
| 全量商品 | 每天 1 次（UTC 19:37 = 北京 03:37），耗时约 26 分钟 |
| 价格刷新耗时 | 83 秒（批量接口 `dynamicv2`，60 个/请求） |
| 数据存放 | 独立 `data` 分支，由 Actions 自动推；`main` 只有代码 |
| 产物 | `public/goods.json`（~2MB）、`public/meta.json`、`public/prices/latest.json`、`public/prices/<月>.jsonl`（**按次追加，不覆盖历史**） |
| ⚠️ 残缺快照 | 有。样本中最少的一次**只覆盖 54 个商品**（正常约 1,480）→ 部分失败**没有告警**，只在数据里看得见 |

### 判断
管线是真的在跑（`data` 分支提交记录可验），但**恢复能力弱**：失败了没人知道，也没有补采。

## 四、最大的缺口：底座和产品是断开的

实测确认：**小程序里没有任何一处引用数据底座**（唯一命中的是本地存储键名 `goodsdex:data:v1` 和导出文件名前缀，不是数据）。

也就是说：
- 3,915 条商品档案 → 产品没用上，用户还是**手打型号**
- 7 天价格序列 → 产品没用上，"折损"靠**手动填参考价**
- 转转估值 → 产品没用上，旧机残值靠**用户自己估**

## 五、优先级（待拍板）

1. **历史深度是硬伤**，两条路：
   - (a) **现在就开始攒** —— 3 个月后才够用（时间换数据，零成本但要等）；
   - (b) **找外部历史价格源补齐**（如历史比价站 / 二手成交记录）—— 需评估合规与可得性。
2. **产品接入**，按性价比排：
   - ① **接商品档案**（选机型代替手打）—— 数据现成，体验提升最直接；
   - ② **接转转估值**（旧机残值自动填）—— 接口已封装，接上就能用；
   - ③ 接价格序列（到价提醒的"历史最低"）—— 数据只有 7 天，先做入口、不承诺深度。
3. **加失败告警**：残缺快照要能被发现（现在坏了只有翻数据才看得见）。
