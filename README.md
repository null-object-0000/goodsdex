# GoodsDex

> 商品数据索引：从多源采集商品信息，字段级溯源，可验证、可对账。

给一个商品分类，枚举出全部商品，从多个数据源采集，合并成**每条数据都能追溯来源**的结构化数据集。

## 为什么需要它

做「这东西该不该换/该不该买」这类判断，需要三类数据：

1. **参数** —— 官方最准，但常以图片形式存在，且新品滞后
2. **时间** —— 官方参数页往往只给到月，精确到日要另找源
3. **价格与残值** —— 官方价在接口里；二手残值要靠平台（转转/爱回收）

现有做法各有毛病：爬虫只取一个源、解析器写死页面结构、数据没有溯源、冲突被静默覆盖。
GoodsDex 的核心主张是：**数据必须可溯源、冲突必须留痕、宁可缺不可错**。

## 核心原则

**① 三路并查** —— 抓任何页面前，先看三层：

| 层 | 手段 | 能看到什么 |
|---|---|---|
| raw HTML | curl/urllib | 服务端渲染的部分，或 SPA 空壳 |
| 渲染后 DOM | CDP `Runtime.evaluate` | JS 注入的内容 |
| 网络请求 | CDP `Network.*` | **隐藏的数据接口**（最高价值，最容易漏） |

实战教训：小米商城 PC 商品页的 raw HTML 是空壳，真正的数据在
`api2.order.mi.com/product/view` —— 只有看网络请求才发现。若只看 HTML，会误判"没有数据"。

**② 三层证据结构** —— 不边采集边合并：

```
Capture     一次采集的完整证据（原响应 + 状态 + 内容哈希 + 时间）
Assertion   谁对哪个属性、在什么条件下声明了什么（含真实定位）
View        按策略选出的展示值（可重建，不是事实本身）
```

适配器返回**断言列表**，不按字段名去重 —— 同值多源是独立佐证，全部保留。

**③ 严格匹配，宁缺勿错** —— 第三方源按名称查找时，词条名必须与商品名**完全一致**。
0.77 相似度的模糊匹配曾把「REDMI Buds 8 青春版」匹配到「REDMI Buds 8 Pro」——
这种错误比没有数据更危险。

**④ 冲突留痕** —— 多源冲突不静默覆盖，全部保留并分类：

- `compatible`：可能兼容（`约5.3g` vs `5.3±0.1g`），但不宣称事实相等
- `incomparable`：条件不同（降噪开/关续航），不可比
- `conflict`：真正互斥，需人工核查

**⑤ 区分"没抓到"和"官方没有"** —— 采集失败、限流、官方未提供是**三件不同的事**。
混在一起就会得出"数据质量差"的错误结论。用 `CaptureStatus` 与缺口原因区分：

```
success | partial | transport_error | rate_limited | source_error | parse_error
缺口原因：source_empty（源未提供）| absent（确实没有）| not_collected（采集失败）
```

## 架构

```
src/goodsdex/
  facts.py             Capture / Assertion / Bundle（证据层）
  resolve.py           断言 -> 视图（单位/否定/条件解析；品类规则）
  identity.py          商品身份：Product / Variant（product_id vs commodity_id）
  kind.py              类型分流：整机 / 配件耗材 / 服务
  category_filter.py   分类形态过滤（官方搜索是模糊匹配，会互相污染）
  multi_model.py       多型号条目拆分（一个 product_id 覆盖多个型号时）
  vision_extract.py    视觉参数提取（官方把参数放在图片里）
  vision_normalize.py  属性归一化（同义写法收敛 + 包装附件分离）
  compare.py           类型化 A/B 对比
  coverage.py          覆盖度统计（对应下游价值，不是字段数）
  economics.py         换机经济（残值 / 保值换新 / 盈亏平衡）
  pipeline.py          采集主流程
  sources/
    mi_cn.py           小米商城官方（PC + 移动端）
    zhuanzhuan.py      转转开放平台（残值行情，需凭证）
scripts/
  crawl_all.py         全量采集（84 分类，可断点续跑）
  audit_usability.py   数据可用率审计
  vision_params.py     视觉参数提取（预筛 + 提取 + 合并）
  img_preselect.py     规格图零成本预筛
  compare_all.py       跨商品参数对比
  compare_vision.py    视觉数据对比
  apply_split.py       应用多型号拆分
  analyze_all.py       全库分析
  should_i_upgrade.py  端到端：该不该换
tests/                 6 套 73 项
docs/
  methodology.md       抓取方法论与实战案例
  REVIEW-codex.md      设计评审
```

## 用法

```bash
export PYTHONPATH=src          # 仓库尚未打包
export PYTHONPATH=src:scripts  # 跑 scripts 下的脚本时需要

# 采集
python3 -m goodsdex.pipeline --list-categories
python3 -m goodsdex.pipeline --category 吹风机
python3 scripts/crawl_all.py --resume

# 对比
python3 scripts/compare_all.py 冰箱

# 视觉提取（官方把参数放图片里的品类）
python3 scripts/vision_params.py --category 壁挂空调 --limit 3 --write

# 该不该换
python3 scripts/should_i_upgrade.py --device "Xiaomi 15 Pro" \
    --price 5299 --bought 2026-01-15 --residual 2400-2800 --new-price 5999 --trade-in
```

## 数据源

**已接入**

```
小米官方-移动端 mtop   ← 主力：参数/价格/销量/口碑/问答
小米官方-PC 详情       ← 补充：图文详情、购买选项、规格图
转转开放平台           ← 残值行情（需注册凭证，见 sources/zhuanzhuan.py）
```

**已排除**

- **小米国际站/香港站** —— 区域版本，型号体系与国行不同（港版 `M2535E1`），
  配色命名也不一致，混入会污染型号主键。
- **百度百科** —— 想用它补"精确到日的发布时间"，但实测**补不上**：
  吹风机 11 款官方无发布日期，百科也全无；耳机抽样 8 款仅命中 1 款。
  且它是唯一会**主动产生错误**的源（把"前代产品于2020年发布"当成本产品发布日期）。

## 实测数据形态（重要）

**91% 的家电参数不在接口里**，而在商品详情的长图中。

- 手机全系：接口 100% 有结构化参数
- 吹风机：91%
- **冰箱：17/23 有参数**（命名高度一致，可直接对比）
- **空调/扫地机/音箱/路由器等：0%** —— 接口的 `tab_content` 全是
  `plain_view` 图片（2564px 长图），无任何结构化文字字段

所以视觉提取不是锦上添花，是**必需品**。但要做对：

1. **tab 命名无规范** —— 空调叫「规格参数」，冰箱叫「256L(星锻银)」。
   用排除法（排除服务类 tab）而非名字匹配。
2. **成本必须先控** —— 一个商品可能有 100+ 张图。用零成本特征
   （白底/低彩/长宽比）预筛，冰箱 100 张 → 5 张。
3. **预筛要按 tab 配额** —— 否则某个 tab 的长图挤占全部名额，
   其他型号的参数完全提取不到。
4. **属性名必须归一化** —— 同一事实有 `额定制冷量(W)` / `额定制冷量（W）` /
   `额定制冷量 (W)` 多种写法；不做归一化无法跨商品对比。
5. **包装清单要分离** —— `7号干电池` / `使用安装说明书` 不是产品参数。

## 多型号条目

一个 `product_id` 可能覆盖**多个型号**。「米家冰箱 三门系列」的 tab 是
`256L(星锻银)` / `271L(全域离子净化)` / `215L` / `风冷-216L` / `直冷-216L`——
5 个不同型号，规格各异。当成一台对比会得到 `103.1cm/216 L/256L/2...` 的拼接垃圾。

拆分依据在数据里：每个 tab 的视觉参数自带**产品型号**（`MC-256WTMPN`）。

**接口参数不塞进子记录** —— 接口只给一份，无法自动判定归属，宁缺勿错，
标为 ambiguous。全库 930 台整机中 24 台（3%）属此类。
